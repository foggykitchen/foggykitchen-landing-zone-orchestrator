# Azure Bulk Ingestion Pipeline Pattern

This directory contains the shared **Azure bulk_ingestion_pipeline** pattern used by FoggyKitchen Landing Zone Orchestrator.

It composes one bulk ingestion flow:

- Blob Created events from an ingestion container invoke `fnbulkload` through Event Grid
- `fnbulkload` reads uploaded JSON blobs and publishes records into one Event Hub
- `fncollector` consumes the Event Hub through native Azure Functions bindings
- `fncollector` persists records into PostgreSQL Flexible Server over delegated-subnet private access
- validation-only API Management `GET /validate` invokes `fnvalidator` to prove that PostgreSQL contains an expected row

## Summary

This is a public orchestrator pattern for the Azure Functions/event-driven teaser tier.

It deliberately excludes:

- Service Connector Hub or Service Bus equivalents
- hand-authored API Management policy XML
- API Management and `fninitiator` HTTP ingestion for data entry
- PostgreSQL Entra authentication, customer-managed keys, or diagnostics
- private endpoint variants for the Function App, Storage Account, Event Hub, API Management, or PostgreSQL
- CI/CD or Azure DevOps deployment pipelines
- hub-and-spoke, firewall transit, multi-region, and governance composition

Those richer concerns belong in a future private blueprint layer or later narrowly scoped PRs. API-driven ingestion stays in the separate Azure `event_driven_data_pipeline` pattern so the Azure Functions family remains aligned with the OCI split between event-driven and bulk ingestion. This pattern exposes API Management only for the validation-only `fnvalidator` endpoint.

## What It Creates

- one Resource Group
- one self-contained VNet
- one subnet for Functions regional VNet integration
- one delegated PostgreSQL subnet
- one NSG associated with the Functions integration subnet
- one private DNS zone linked to the VNet for PostgreSQL delegated-subnet private access
- one Storage Account used by the Function App runtime and private ingestion container
- one user-assigned managed identity for the Function App
- one Event Hubs namespace with one Event Hub
- RBAC assignments for Event Hub sender/receiver access and Storage Blob Data Reader access
- one PostgreSQL Flexible Server with public network access disabled
- one Linux Function App ZIP deployment containing `fnbulkload`, `fncollector`, and `fnvalidator`
- one API Management instance exposing validation-only `GET /validate`
- one Event Grid System Topic and subscription routing Blob Created events to `fnbulkload`

## Azure Platform Notes

The pattern follows Azure-native serverless behavior rather than porting OCI resources literally.

- Event Hub-triggered Functions use native Azure Functions trigger bindings. There is no Service Connector Hub resource.
- Event Grid routes Blob Created events directly to the Azure Function endpoint. There is no separate connector resource.
- API Management policy XML is generated by `terraform-az-fk-api-management` from the `routes` input.
- The current Function module deploys one Function App package. Named functions are defined in the ZIP content, so the pattern uses one module instance containing all runtime functions.
- Storage Account network rules allow Azure services and the Functions integration subnet while keeping the ingestion container private.
- PostgreSQL public network access is disabled.
